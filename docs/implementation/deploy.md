# Выкладка на сервер

Родительский индекс: [index.md](index.md) · Локальная разработка — [development.md](development.md)

Словарь опубликован как **`https://recnik.srpski.pasha-home.ru`** и открыт всем: ни пароля,
ни клиентского сертификата. Живёт он на домашней платформе `app-server` (VPS в Yandex Cloud)
пятым приложением рядом с CardDAV, «Моим кругом», Learning API и TimeLimit.

**Хозяин серверной части — репозиторий `home-infra`**: роль `app-server/roles/app_vocabulary`,
плейбук `app-server/playbooks/vocabulary.yml`, страница `docs/apps/vocabulary.md`. Здесь
описано только то, что касается самого словаря.

## Что выкладывается

Один артефакт — jar. `bootJar` собирает веб-оболочку (`npm run build`) и кладёт её внутрь
статикой, поэтому Vue приезжает на сервер вместе с бэкендом и отдаётся им же.

Так сделано из-за устройства платформы: общий nginx умеет на одном сайте **либо** статику,
**либо** проксирование, и заводить смешанный случай в общей роли ради одного приложения дороже,
чем собрать один артефакт. Плата за это — правка одной кнопки в оболочке требует пересборки jar.

Разработку это не задевает: `bootRun` статику не собирает, страницу по-прежнему отдаёт
`npm run dev` со своим проксированием `/api`.

Два места, которые нужны только выкладке:

- `ShellController` возвращает оболочку по адресам `/word/**` — иначе прямая ссылка на статью
  и перезагрузка страницы давали бы 404: такие адреса знает только маршрутизатор Vue;
- `/actuator/health` — по нему живость проверяют роль выкладки и внешняя проверка.

## Настройки на сервере

Подключение к базе приезжает **окружением**, файла `secrets.properties` на сервере нет:

| Переменная | Значение на сервере |
|---|---|
| `VOCABULARY_DB_URL` | `jdbc:postgresql://db:5432/vocabulary` |
| `VOCABULARY_DB_USERNAME` | `vocabulary` |
| `VOCABULARY_DB_PASSWORD` | `vault_vocabulary_db_password` из `secrets/app-server.yml` |

Имена совпадают с ключами `vocabulary.db.*` из `secrets.properties`: Spring читает и то, и
другое как одно свойство. Пароль заводится один раз — `cfg ansible config init app-server`.

## Обновить приложение

```bash
cd ~/Projects/home/home-infra/app-server
ansible-playbook playbooks/vocabulary.yml -e @../secrets/app-server.yml
```

Плейбук сам собирает jar в этом репозитории (Java 25), кладёт его на сервер и перезапускает
compose-проект. Миграции Flyway применяются при старте, как и локально.

## Обновить содержимое словаря

```bash
./scripts/upload-data.sh
```

Слепок локальной базы (`pg_dump --clean --if-exists`) уезжает на сервер и заливается в базу
контейнера; на время заливки контейнер приложения останавливается — слепок сносит и создаёт
заново те же таблицы, из которых оно читает. В конце скрипт сам проверяет, что словарь
отвечает и сколько статей находит.

Направление одно: **ноутбук → сервер**. Обратного нет и не должно появиться, пока правка через
сайт не сделана: на сервере нет ничего, чего не было бы здесь.

Отсюда же следует, почему базы словаря нет в резервных копиях платформы: восстановление после
потери ВМ — это плейбук плюс этот скрипт. Появится модерация статей — данные на сервере станут
единственными, и каталог придётся завести в `app_backup` (условие записано в
`home-infra @/docs/apps/vocabulary.md`).

## Границы

- Postgres на сервере — **18-й** версии: слепок, снятый `pg_dump` 18, в 16-ю не восстановится.
- Лимиты памяти: 512 МБ приложению, 256 МБ базе. ВМ у платформы одна на все приложения, всего
  2 ГБ; после выкладки словаря свободно ≈860 МБ.
- 🚨 Пароль базы в тексте задачи, коммите и выводе команд не появляется: наружу идёт ссылка на
  запись в vault, а не значение.
